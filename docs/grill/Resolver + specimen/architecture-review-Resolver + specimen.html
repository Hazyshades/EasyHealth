Make Resolver decision identity deep

The specimen hot spot is not only selection; it is whether a past decision can be named and reproduced.

Files
src/lib/biomarkers/types.ts:405–428

Problem

The Resolver reads specimenSource and capturedHeading, but buildInputEvidenceHash omits both. A stated specimen and a reviewed-panel specimen can share the same specimen value while carrying different evidence, yet their input identity remains equal. The writer request hash includes the full trace, so immediate idempotency is not proven broken; historical identity and reprocessing still have a gap.

Solution

Make decision identity a deep module that canonicalizes every field able to alter resolution, including provenance source and heading-match context. Let the writer, reprocessing diff, and corpus adapter consume it. Keep raw OCR out of the persisted trace; hash a canonical redacted representation.

Wins
  • • locality: one identity rule
  • • leverage: stable reprocessing diffs
  • • interface: provenance stays visible
  • • testability: stated ≠ policy
ADR fit. ADR 0001 remains intact: one Registry runtime, no guessed specimen. This makes that decision more inspectable rather than adding another runtime.

Collapse duplicate evidence admission

Two production adapters currently decide which row evidence is allowed to reach the Resolver.

Problem

The review and writer builders both clean overrides, filter unstated axes, construct provenance, and apply reviewed-panel specimen policy. Their separate implementations are a real seam: preview, acceptance, correction, reprocessing, and the Health Profile can drift in ordering or in the evidence admitted.

Solution

Make evidence admission a deep module. Keep a thin adapter for each source row shape, then pass one admitted evidence record into the Resolver. Apply stated-axis filtering before panel policy in one place.

Wins
  • • locality: one admission rule
  • • leverage: policy ordering once
  • • interface: clean Resolver input
  • • testability: one specimen seam
Deletion test. Remove either current builder. If the same filtering and policy decisions reappear in callers, the module is shallow; a shared admission module earns depth.

Keep persisted decisions off the live Resolver

A persisted decision should remain a historical read, not a current-catalog computation.

Files

Problem

For rows with an active revision, buildNormalizationReview still calls resolveMeasurementDefinition(input) before projecting the persisted result. The active projection reads resolver_evidence, while the technical trace reads resolver_decision_trace; one historical decision has two read shapes.

Solution

Deepen a persisted-decision read module. Active revisions use revision-owned trace and projection only; the live Resolver stays at the explicit pre-revision preview seam. Concentrate trace summarization and eligibility reading without removing the deliberate legacy evidence field yet.

Wins
  • • locality: historical semantics
  • • leverage: version-stable review
  • • interface: trace is test surface
  • • testability: active ≠ preview
ADR fit. ADR 0001's one-runtime decision is preserved. This follows the EH-115 historical-trace intent: a current catalog must not silently rewrite an accepted decision.

Concentrate Registry release identity

The one-runtime decision is strong; its release identity is still assembled in several callers.

Problem

Release fields and digest provenance are manually assembled in the writer, automatic verification, reprocessing diff, and corpus paths. captureDeployedRelease() centralizes them only for reprocessing, while trace creation still receives several independent release values.

Solution

Make Registry release identity a deep module that owns the manifest digest and resolver, normalization, policy, and trace versions. Let decision, trace, reprocessing, and corpus records consume one captured release.

Wins
  • • locality: version bumps once
  • • leverage: identical dry-run/live stamps
  • • interface: release is explicit
  • • testability: digest drift is visible
ADR fit. ADR 0001 preserves one Registry runtime. Its historical version table is not source of truth; any release module must read the live manifest and constants.

Make the release corpus a real Resolver adapter

The corpus is a valuable release gate, but its input composition is a third implementation-shaped path.

Files

src/lib/documents/stated-axis-evidence.ts:1–204
src/lib/documents/normalization-review.ts:213–290
src/lib/documents/observation-normalization-writer.ts:187–248
Problem

The release corpus manually reconstructs Resolver input from source text, section context, stated axes, and heading context. Production has two different row adapters. The gate can remain green while a production adapter changes override, reference, or value-kind admission.

Solution

Give the corpus a mutation-free release adapter over the shared evidence-admission module. Preserve its fixture-specific source shape, but remove a second copy of production admission decisions.

Wins
  • • locality: gate follows production
  • • leverage: release evidence stays honest
  • • seam: fixture data remains isolated
  • • testability: admission drift fails early
Why speculative. This depends on the evidence-admission choice above. Forcing the script through a production row shape could make the test seam less clear rather than deeper.
