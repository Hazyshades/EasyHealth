Laboratory assessment admission

Corrected architecture review after Q1–Q5: a deep module for deciding whether persisted laboratory observations may enter the Health Profile assessment read model, without taking ownership of reported-result visibility, freshness, score groups, or the Resolver.

What was wrong in the previous wording

Correction
  • The eligibility decision is not absent. projectLaboratoryOutcome already carries the assessment exclusion reason from evaluateAssessmentEligibility. The lossy point is projectHealthProfileLaboratoryInput: it returns null, and buildHealthProfileSnapshot calls the outcome projection again to reconstruct an exclusion.
  • Reported counts do not belong to admission. projectHealthProfileReportedResults owns its buckets and visibility summary. Admission may provide explanation data, but it must not decide whether a factual reported row is shown or counted.
  • The deletion test was overstated. Removing the proposed module would duplicate interpretation and gating of an already-produced Resolver result, not the Resolver itself. Registry 2.0 and Resolver remain upstream authorities.
  • Censored values require two outcomes. EH-164 intentionally returns a text marker with a reviewed binding so readiness can report “present but invalid”; it never becomes a finite numeric contributor. A contract that equates “excluded” with “no Health Profile marker” would break this behavior.

Settled boundary

Assessment admission
Checks a persisted laboratory observation after canonical Resolver output and reviewed Registry 2.0 binding. It does not evaluate freshness, required groups, score role, contribution selection, or formulas.
Reported result
A factual laboratory result retained for display and explanation independently of admission. An excluded result can remain visible.
Score readiness
A downstream Health Profile decision over admitted inputs: freshness, numeric usability, document-native bounds, required groups, and score policy.
Scope
Reuse the admission decision where assessment admission is actually decided. Do not make Biomarkers, review, reports, structured context, or Document list visibility depend on it.

Proposed contract

This is a concrete contract, not an implementation plan. The discriminant must distinguish Resolver outcome from admission decision and must preserve EH-164’s safe text marker.

Conceptual result

AssessmentAdmissionDecision
  = {
      kind: "accepted";
      input: HealthProfileLaboratoryInput;
      evidence: AssessmentAdmissionEvidence;
    }
  | {
      kind: "excluded";
      reason: AssessmentExclusionReason;
      evidence: AssessmentAdmissionEvidence;
    };

AssessmentAdmissionEvidence = {
  assessment: {
    exclusionReason: AssessmentExclusionReason | null;
    assessmentInputKey: string | null;
  };
  resolution: LaboratoryResolutionDetails;
  resolverTrace: ResolverDecisionTrace | null;
  binding: {
    measurementDefinitionKey: string | null;
    analyteKey: string | null;
    registryBindingReady: boolean;
    verificationStatus: VerificationStatus | null;
  };
  canonical: {
    outcome: ResolverResult | null;
    incompleteReason: IncompleteReasonClass | null;
  };
};

Trace boundary: carry a validated full Resolver trace when a consumer needs candidate-level explanation. Existing ScoreExclusion and canonical snapshot hash require the summarized resolution fields and canonical projection below; they do not require candidate arrays in the hash.

Contract invariants

  1. Input is a persisted laboratory observation. An unlinked extracted row never enters this module; it remains reported evidence.
  2. The module consumes active Resolver/Registry 2.0 output and reviewed binding. It never resolves labels, selects candidates, or uses a fallback catalog.
  3. First-failure order remains deterministic for ordinary numeric rows: revision, resolution, binding, verification, value kind/value, then document-native reference range. Censored text takes the intentional non_numeric_value marker branch before reference-range checks.
  4. Freshness, latest identity, required groups, score roles, contribution groups, formulas, and recalculation lifecycle remain downstream.
  5. Accepted does not mean “numeric contributor.” A censored result with a reviewed binding is accepted as a text marker even when its reference range is missing or malformed; Health Profile marks it invalid and never scores it.
  6. Reported-result counts and visibility are not fields or policies of admission. A separate reported projection consumes factual rows and, if needed, admission evidence.
  7. Snapshot-only metadata such as source regions, system fallback, and ScoreExclusion remains an adapter concern, not admission.
Important existing edge: projectHealthProfileReportedResults currently increments ready_for_scoring_count when assessment_input is non-null. EH-164’s censored marker is non-null but not numeric-scoreable. Do not silently change this metric during the admission refactor; either preserve it as an existing contract or separately rename/redefine the reported metric with explicit evidence.

Acceptance invariants before implementation

Must remain identical

  • Scores, readiness groups, freshness statuses, and provenance for identical admitted inputs.
  • Reported-result rows, visibility, and source counts for identical extracted inputs.
  • EH-164 text-marker behavior and no numeric contribution.
  • Canonical snapshot hash, including exclusion and reported-row evidence.
  • HTTP/worker parity and no GET-time synthesis contract.

Must be explicit if changed

  • Meaning of ready_for_scoring_count for accepted nonnumeric markers.
  • Any new assessment exclusion reason, especially unit incompatibility.
  • Whether evidence carries only the primary reason or secondary failed gates.
  • Any requirement that persisted observations retain a source document id.
  • Any extension from Health Profile assessment admission to other consumer axes.
Recommendation: proceed with the admission contract above. The next implementation step should be a call-site migration plan and a focused contract verifier, not a new Resolver or a change to reported-result policy.
