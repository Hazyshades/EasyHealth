## ADDED Requirements

### Requirement: Versioned synthetic golden fixture pack
The repository SHALL maintain a versioned synthetic assessment golden fixture pack that covers all eight named body systems. Fixtures SHALL use only synthetic or de-identified values. Each case SHALL declare a stable id, a family, inputs, and committed per-system expected outputs. The pack SHALL identify the Health Profile score algorithm version it locks.

#### Scenario: Pack names every named system
- **WHEN** a maintainer inspects the EH-147 golden pack
- **THEN** it includes cardiovascular, metabolic, thyroid, liver, kidney, blood, nutrients, and inflammation
- **AND** every case has a stable id and committed expected outputs
- **AND** no fixture contains real patient data

#### Scenario: Expected outputs are per-system
- **WHEN** a golden case is evaluated
- **THEN** its expected outputs include each relevant system's `scoreability` and `state_score`
- **AND** incomplete systems include the expected readiness reason codes
- **AND** the committed expected outputs are not regenerated by the CI run

### Requirement: Representative range, unit, missing-group, and correction coverage
The golden pack SHALL include fixture families for complete in-range evidence, complete out-of-range evidence, SI versus US unit presentation, a missing required group on every scoreable system, unusable or inverted document-native ranges, context-only substitutions that must not unlock readiness, approved alternatives that must unlock readiness, inflammation as factual-only, and pending versus `manually_corrected` assessment admission.

#### Scenario: Complete in-range evidence scores seven systems and not inflammation
- **WHEN** the complete in-range golden case is evaluated
- **THEN** each of cardiovascular, metabolic, thyroid, liver, kidney, blood, and nutrients is `scoreable` with a non-null `state_score`
- **AND** inflammation is `non_scoreable` with `state_score` `null`

#### Scenario: Out-of-range values remain scoreable with a lower score
- **WHEN** the complete out-of-range golden case uses the same required groups as the in-range case with values outside document-native bounds
- **THEN** each scoreable system remains `scoreable`
- **AND** each scoreable system's `state_score` is strictly less than the corresponding in-range score

#### Scenario: SI and US presentation preserve classification
- **WHEN** a unit-family golden case is evaluated under SI and US laboratory unit systems
- **THEN** scoreability and in-range versus out-of-range classification match the committed expectation
- **AND** displayed units and converted values follow existing presentation rules
- **AND** missing conversion is not invented for markers without a unit family

#### Scenario: Missing required group yields a null score
- **WHEN** a missing-group golden case omits every alternative from one required group of a scoreable system
- **THEN** that system's `scoreability` is `incomplete`
- **AND** its `state_score` is `null`
- **AND** readiness reasons include code `missing` for that group
- **AND** no partial average or `0` is substituted

#### Scenario: Unusable document range does not satisfy readiness
- **WHEN** a required alternative is present without a usable document-native reference bound
- **THEN** the group is not satisfied
- **AND** the system `state_score` is `null`

#### Scenario: Inverted document range is excluded at admission
- **WHEN** an admission-seam golden row has finite `ref_low` greater than finite `ref_high`
- **THEN** assessment eligibility is false with `invalid_document_reference_range`
- **AND** the row does not enter Health Profile scoring

#### Scenario: Context-only input cannot replace a required group
- **WHEN** a context-only golden case substitutes a context-only measurement for a required group
- **THEN** the system remains `incomplete`
- **AND** its `state_score` is `null`

#### Scenario: Approved alternative satisfies its group
- **WHEN** an alternatives golden case uses one approved alternative in a required group and satisfies every other group
- **THEN** that system is `scoreable`
- **AND** the group's `satisfied_by` key is the committed alternative

#### Scenario: Inflammation remains factual-only
- **WHEN** an inflammation golden case includes a supported CRP observation
- **THEN** inflammation `scoreability` is `non_scoreable`
- **AND** its `state_score` is `null`

#### Scenario: Pending correction is excluded and manually corrected is admitted
- **WHEN** the same resolved numeric reviewed row is evaluated with verification status `pending` and again with `manually_corrected`
- **THEN** the pending row is ineligible with `verification_required`
- **AND** the `manually_corrected` row is eligible
- **AND** only the eligible row may affect Health Profile readiness or score

### Requirement: Fail-closed golden runner and regression report
The repository SHALL provide an executable command that evaluates the golden pack against production Health Profile admission, readiness, scoring, and presentation functions. The command SHALL exit non-zero on any mismatch. It SHALL write a regression report containing the pack hash, algorithm version, case counts, and failed case ids. Repeated runs with the same checkout SHALL be deterministic and SHALL NOT write database rows or require network access.

#### Scenario: Technical check fails on expected-output drift
- **WHEN** `pnpm test:eh147` runs and a committed `state_score`, `scoreability`, eligibility reason, or readiness code does not match production output
- **THEN** the command exits non-zero
- **AND** the report names the failing case id

#### Scenario: Runner is pure and repeatable
- **WHEN** the technical check is executed twice on the same checkout
- **THEN** it uses only committed synthetic fixtures
- **AND** it does not require patient data, network access, an authenticated browser, or database writes
- **AND** both runs produce the same pass/fail result and pack hash

#### Scenario: CI registers the technical gate
- **WHEN** the Measurement Registry verify job runs on a pull request that includes this change
- **THEN** `pnpm test:eh147` is workflow-reachable
- **AND** the suite is listed in `ci/verification-suite-policy.json`

### Requirement: Clinical Product sign-off is hash-bound and not claimed without evidence
The repository SHALL record Clinical Product sign-off against the SHA-256 of the canonical golden pack. Technical CI SHALL NOT require that approval. A product-acceptance check SHALL fail closed when the approval is missing, stale, or bound to a different pack hash. Documentation and the EH-147 QA checklist SHALL NOT state that Health Profile v1 is accepted while sign-off is pending.

#### Scenario: Technical CI passes without product approval
- **WHEN** every golden case matches production output and `QA/eh-147/approvals.json` has no current Clinical Product approval
- **THEN** `pnpm test:eh147` still passes
- **AND** `pnpm check:eh147` fails closed
- **AND** the sign-off matrix records Clinical Product approval as pending

#### Scenario: Stale approval does not accept the pack
- **WHEN** the golden pack hash changes after a previously recorded Clinical Product approval
- **THEN** `pnpm check:eh147` fails closed until a matching approval is recorded
- **AND** Health Profile v1 SHALL NOT be described as accepted
