# Design: eh-151-scoped-expiring-share-links

## Context

There is no share-link table or public token route. Existing report APIs resolve a signed-in profile and `noStoreJson` is used for sensitive JSON, but neither mechanism authenticates an unauthenticated recipient. A public link must become a narrow capability, not a second report API.

## Goals / Non-Goals

**Goals:**

- Create expiring, revocable links for validated reports with exact resource scope.
- Keep bearer tokens and plaintext PINs out of persistent data and logs; persist only the keyed token digest and, when enabled, the salted slow PIN verifier material.
- Fail closed for invalid, expired, revoked, cross-profile, and out-of-scope requests.
- Make public responses uncacheable and non-indexable.

**Non-Goals:**

- Owner share listing/revoke UI or access-history presentation; EH-152 owns those surfaces.
- Anonymous account creation, comments, editing, or report generation.
- A wildcard "all profile data" share scope.

Implementation prerequisite: `make-document-deletion-durable` is a hard prerequisite. EH-151 consumes its committed document tombstone, `write_generation`, report invalidation, whole-report purge, and owner report-delete transition; the public share route never infers source deletion from a missing row or bypasses the durable lifecycle.

## Decisions

### 1. Model share scope explicitly

Add a migration for `report_share_links`, `report_share_documents`, and `share_replacement_operations`.

`report_share_links` stores `id`, `profile_id`, `report_id`, `token_digest`, `token_key_version`, optional `pin_hash` and `pin_salt`, `expires_at`, `revoked_at`, `download_policy`, `allowed_export_formats`, `created_at`, and `last_accessed_at`. Its `profile_id` foreign key references the owner profile with `ON DELETE CASCADE`, and its `report_id` foreign key references `reports(id) ON DELETE CASCADE`. `report_share_documents` stores explicit raw-document IDs with `share_id ON DELETE CASCADE` and `document_id ON DELETE CASCADE`. `share_pin_proofs` stores `id`, `share_id`, keyed `proof_digest`, `issued_at`, and `expires_at`; its `share_id` foreign key uses `ON DELETE CASCADE`, `proof_digest` is unique, and `expires_at` is indexed. `share_replacement_operations` is the authoritative idempotency record and stores `id`, `profile_id`, `predecessor_share_id`, `successor_share_id`, a bounded opaque `idempotency_key` constrained to 1–128 printable ASCII bytes from `[A-Za-z0-9._~-]`, `operation_status` constrained to `committed`, and `created_at`; both share foreign keys use `ON DELETE CASCADE`, and it has a unique `(profile_id, predecessor_share_id, idempotency_key)` constraint plus a unique predecessor constraint ensuring one committed successor. The successor, proof, and operation rows are deleted with the owner profile. No operation or proof row stores plaintext token/PIN material.

`download_policy` is `none` (view only), `report` (validated report plus only the formats in `allowed_export_formats`), or `documents` (the same report access plus explicitly scoped raw documents). `allowed_export_formats` accepts only `pdf`, `csv`, or `json` and defaults to an empty array; raw-document permission never implies a report export format. No row stores a plaintext token, PIN, storage path, or unrestricted profile ID in a public response.

`report_share_access_events` is the durable minimized event store. Its non-null `share_id` foreign key uses `ON DELETE CASCADE`; rows store `id`, `share_id`, `occurred_at`, `result`, `resource_kind`, `client_class`, and `retention_expires_at`; they never store raw IP, full user agent, URL/token, PIN, report title, or source text. EH-151 writes a share-scoped event only after the token selects a share and the route has made its decision, including PIN, resource, expiry, revocation, and rate-limit outcomes. Malformed or unknown tokens have no share row; their rate limiter emits only aggregate telemetry without a token, PIN, or share identifier and they do not appear in owner history. EH-151 owns event writes and retention cleanup; EH-152 consumes the read projection.

The authoritative retention setting is `SHARE_ACCESS_EVENT_RETENTION_DAYS`, default `30`, with an inclusive production range of `1..90`; EH-154 records the deployed value before release. `retention_expires_at` is `occurred_at + retention_days` in UTC. The EH-151 migration defines service-only `public.cleanup_report_share_access_events`, which calls `pg_try_advisory_xact_lock` with a stable lock key, returns `skipped=true` without deleting when another worker owns the transaction-scoped lock, and otherwise repeatedly deletes expired rows in 500-row batches until none remain or a maximum of 100 batches is reached. It returns deleted count, remaining-expired count, and an exhaustion flag. `worker/src/index.ts` invokes this RPC from the existing `tick()` loop when `SHARE_ACCESS_EVENT_CLEANUP_INTERVAL_MS` (default `3_600_000`) is due; `worker/src/env.ts` validates the setting. If the lock is busy or exhaustion is set, the worker schedules a continuation after `SHARE_ACCESS_EVENT_CLEANUP_RETRY_INTERVAL_MS` (default `60_000`) instead of waiting an hour, emits `share_access_event_cleanup_backlog` when rows remain, and repeats until the backlog drains. The transaction-scoped advisory lock releases with the RPC transaction. Cleanup failures use bounded retry/backoff and emit the structured `share_access_event_cleanup_failed` worker error to the deployment log/alert sink; missing cleanup or backlog-drain evidence blocks the privacy gate.

### 2. Use a high-entropy one-time-displayed token

Generate a token as `v<token_key_version>.<random>` where `random` contains at least 32 bytes from the platform cryptographic RNG encoded as base64url. The version prefix is a non-secret selector, not part of the entropy. Return the plaintext token only in the owner creation response. Store `HMAC-SHA-256(key[token_key_version], random)` with a unique index. New links use the active key version; the verifier accepts only configured current/previous versions. If a key version is missing or the key ring is unavailable, verification and creation fail closed; no unkeyed fallback is allowed.

The public route parses the bounded version selector, computes one candidate digest with the corresponding configured key, and performs one indexed lookup; it then requires the matched row's `token_key_version` to equal the selector. Invalid, expired, revoked, malformed, and missing records return the same generic not-found response and do not disclose which condition occurred. Raw tokens are redacted from request/access logs and telemetry. Key rotation is an explicit EH-154 incident/release operation: mint with the new version, accept the old version only during the approved window, reissue or revoke old links, then retire the old key.

### 3. Verify every public request at the capability boundary

Use `/share/[token]` for the page and `/api/share/[token]` for data. The route checks token digest, expiry, revocation, PIN state, the EH-148 read projection's validation status (`valid` or `limited`), validation version, report scope, and requested resource ID on every request. Missing/invalid validation envelopes and legacy reports fail closed; issue codes are used internally and never exposed in public responses. It never calls `getSessionProfileId` as a substitute for token verification. EH-151 owns `src/lib/share-links/public-response-policy.ts` and its `applyPublicShareResponsePolicy(response)` helper; the helper sets `Cache-Control: no-store, private`, `X-Robots-Tag: noindex, nofollow`, a restrictive referrer policy, and the no-third-party-analytics boundary. EH-153's public export adapter SHALL call the same helper before returning PDF, CSV, or JSON. No public export route may emit a permitted file without this policy.

Optional PIN verification uses a slow password hash with a per-share salt and one shared proof lifecycle for every public resource. `POST /api/share/[token]/pin` accepts the PIN only in a non-logged JSON body `{ "pin": "..." }`; it never accepts PIN material in a URL, query, cookie, or response field. After token/share verification and a correct PIN, the route generates at least 32 random bytes, stores only `HMAC-SHA-256(SHARE_PIN_PROOF_PEPPER, proof_random)` in `share_pin_proofs` with `expires_at = now + SHARE_PIN_PROOF_TTL_SECONDS`, and sets an opaque `__Host-eh-share-pin` cookie containing the proof with `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, and no `Domain`. The default proof TTL is `900` seconds and accepts `60..3600`; `SHARE_PIN_PROOF_PEPPER` is required in production. The shared `requireSharePinProof` verifier runs after token lookup and before report reads, EH-153 exports, or raw-document proxy bytes on `/share/[token]`, `/api/share/[token]`, and every approved resource route; it hashes the cookie proof, requires the matching active share row, rechecks token digest, `revoked_at`, `expires_at`, and proof expiry, and clears the cookie on failure. Missing, wrong, expired, revoked, cross-share, or malformed proofs return one generic PIN-required/unavailable response. PIN attempts consume the configured token/requester rate limits; proof rows and cookie values never enter logs, telemetry, access events, URLs, referrers, or public responses. The worker deletes expired proof rows in bounded 500-row/20-batch cleanup and emits only non-secret backlog/failure signals.

The EH-151 migration owns `share_rate_limit_buckets(key_digest, window_started_at, count, expires_at)` with a unique constraint on `(key_digest, window_started_at)`, an expiry index, and the service-only `public.consume_report_share_rate_limit` and bounded `public.cleanup_report_share_rate_limit_buckets` RPCs. The consume RPC uses that unique conflict target to atomically reset an expired window or increment the active row and returns `allowed`, `retry_after_seconds`, and `store_available`. The cleanup RPC deletes at most 500 expired rows per batch and at most 20 batches per invocation, then returns `deleted_count`, `remaining_expired_count`, and `exhausted`. The worker also deletes expired `share_pin_proofs` under the same bounded 500-row/20-batch discipline and emits non-secret proof-cleanup backlog/failure signals. `worker/src/index.ts` invokes these RPCs from the existing `tick()` loop when `SHARE_RATE_LIMIT_CLEANUP_INTERVAL_MS` (default `900_000`) is due; `worker/src/env.ts` validates the interval. If `remaining_expired_count > 0` or `exhausted=true`, the worker schedules a continuation after `SHARE_RATE_LIMIT_CLEANUP_RETRY_INTERVAL_MS` (default `60_000`) instead of waiting for the next interval, retries failures with bounded backoff, and emits `share_rate_limit_cleanup_backlog` while rows remain or `share_rate_limit_cleanup_failed` after retries are exhausted. These cleanup settings and signals are part of EH-154 evidence. `SHARE_TRUSTED_PROXY_CIDRS`, `SHARE_TRUSTED_PROXY_ATTESTATION_KEY`, `SHARE_RATE_LIMIT_PEPPER`, and `SHARE_PIN_PROOF_PEPPER` are required in production; `SHARE_TRUSTED_PROXY_ATTESTATION_MAX_AGE_SECONDS` defaults to `30` and accepts `5..120`; `SHARE_PIN_PROOF_TTL_SECONDS` defaults to `900` and accepts `60..3600`; unset other optional settings use their defaults: `SHARE_RATE_LIMIT_WINDOW_SECONDS=60` accepts `10..300`, `SHARE_RATE_LIMIT_TOKEN_FAILURES=10` accepts `1..100`, and `SHARE_RATE_LIMIT_REQUESTER_FAILURES=30` accepts `1..300`. A missing trusted-ingress configuration/key, rate-limit pepper, proof pepper, or invalid setting denies startup/requests rather than falling back. A store timeout/error denies the request with a generic non-enumerating `503` and no local/process fallback; an exhausted window returns a generic `429` with no token/PIN cause. These named settings are deployment configuration recorded by EH-154.

The trusted-ingress deployment handoff is versioned in `openspec/changes/eh-151-scoped-expiring-share-links/deployment/trusted-ingress.yaml`; the platform owner deploys that artifact as the only public-to-app path. Its `public_https` listener accepts unauthenticated browser share requests without a client certificate, then forwards only through the separate `private_ingress_to_application` HTTPS/mTLS leg to the private Next.js origin. It declares the exact strip/overwrite header list, attestation key reference, and non-forgeable immediate-peer metadata contract on that private leg. `src/lib/share-links/trusted-ingress-transport.ts` defines `TrustedIngressRuntime.getImmediatePeerAddress(request): string | null` and `getTrustedIngressContext(request, runtime): TrustedIngressContext | TrustedIngressFailure`; the runtime adapter receives peer metadata from the hosting connection and never derives it from request headers. `TrustedIngressContext` contains only the verified canonical `edgeVerifiedClientAddress`; `TrustedIngressFailure` maps missing peer/configuration/attestation to generic `503`. Both routes inject the deployment runtime adapter before calling `trusted-ingress.ts`; a runtime without peer metadata or a reachable direct origin returns generic `503` and cannot be marked ready by EH-154. The deployment artifact and transport interface are owned by EH-151's public-boundary owner with platform/deployment review required before route implementation.

### 4. Share snapshots, not authorization shortcuts

A validated report snapshot may be rendered through EH-148's `src/lib/report-read.ts` resolver, which derives source availability from the persisted evidence mapping and current source rows. A source row archived/removed while its parent document remains active remains visible only as a historical snapshot with a `SOURCE_UNAVAILABLE` limitation; the public share never treats the snapshot as live authorization. If the durable deletion transition commits a source document's `deleting`/tombstoned state, EH-148 invalidates the complete report before this route reads it, so owner/share/export return the generic unavailable failure and no snapshot bytes are exposed. The share still checks that the report belongs to the share's profile and is not deleted. Deleting a report cascades its share links, explicit child-document scope, replacement operations, access events, and evidence mappings through the declared foreign keys.

A raw-document request uses a capability-checked proxy/stream route that revalidates the active share, expiry, revocation, report scope, child document allow-list, archive state, and download policy on every request before streaming bytes. It never returns a storage signed URL and never delegates authorization to the storage provider's independent URL lifetime. Revocation or expiry after a recipient has obtained a report or download response cannot retract bytes already received, but a subsequent raw-document request is denied.

### 5. Keep management behind a separate seam

EH-151 exposes owner creation and public read primitives plus the service-only `public.replace_report_share` writer. The RPC accepts authenticated owner/profile identity, predecessor share ID, a bounded opaque owner/share-scoped `idempotency_key` constrained to 1–128 printable ASCII bytes from `[A-Za-z0-9._~-]`, new keyed token digest, and token-key version; it locks the predecessor, first looks up an existing committed operation for that owner/predecessor/key and returns only its recorded operation/successor metadata on replay, then for a new key verifies ownership and active state, reserves the unique `(profile_id, predecessor_share_id, idempotency_key)` operation, copies the immutable report scope/raw-document allow-list/expiry/export policy into exactly one successor, revokes the predecessor in the same transaction, and commits `operation_status=committed`. The unique predecessor constraint prevents a second successor. A different key after predecessor revocation returns a generic conflict. Any mint, reservation, ownership, or RPC failure rolls back the operation and leaves the predecessor active. Only the initial owner creation/replacement response may carry the one-time plaintext link; operation rows, logs, and telemetry never store it. EH-152 owns management list/revoke/replacement endpoints and UI, and no public route may call owner management operations.

## Risks / Trade-offs

- A bearer token can be copied by a recipient. Entropy, expiry, optional PIN, no-store responses, and immediate revoke reduce exposure but cannot make a bearer link non-shareable.
- HMAC pepper rotation invalidates all existing tokens unless a key-version migration exists. Store a key version and document rotation as an incident procedure before release.
- A public page can leak through browser history or screenshots. No-store headers, noindex, restrictive referrer policy, and explicit owner copy warn against forwarding; the remaining risk is accepted for link sharing.
- Public rate limiting needs a shared store in multi-instance deployment. A process-local limiter is not an acceptable production control.
